Forty lines

Part A said a language is worth building. Now: what is one made of?

By the end of this hour you will have built one — forty lines of Python, which run — and seen its two halves:

  • syntax: which programs exist;
  • semantics: what they mean.

We use arithmetic, because you already know what its programs mean.

The characters are not the program

2 + (x * 3)      2+(x*3)      2 +
                              (x * 3)

Same program, three times. What stays fixed is a tree: an addition whose right operand is a multiplication.

The parentheses are not in the tree. They only told the reader which tree: 2 + x * 3 could have been (2 + x) * 3.

Abstract and concrete

The tree is the abstract syntax tree (AST): it has forgotten spaces, brackets, line breaks — everything that does not affect meaning.

The characters are the concrete syntax: one of many ways to write the tree down.

Characters → tree is the job of a parser (Chapter 3). Until then, we write the trees by hand.

Half one

Syntax: which trees exist

The syntax, in Python


from dataclasses import dataclass

@dataclass(frozen=True)
class Number:
    value: float

@dataclass(frozen=True)
class Variable:
    name: str

@dataclass(frozen=True)
class BinaryOp:
    left: Expr
    operator: str
    right: Expr

type Expr = Number | Variable | BinaryOp

Read the last line as a definition: an expression is a number, or a variable, or a binary operation — and nothing else.

The tree for 2 + (x * 3)


example = BinaryOp(
    left=Number(2.0),
    operator="+",
    right=BinaryOp(left=Variable("x"), operator="*", right=Number(3.0)),
)

A BinaryOp contains two further expressions: the definition is recursive, so trees of any depth exist.

frozen=True: a tree never changes after it is built. (Chapter 2 says why.)

The same thing, as a mathematician writes it

\( e ::= n \;\mid\; x \;\mid\; e \; \mathit{op} \; e \)

"An expression is a numeral, or a name, or an expression, an operator and an expression."

This is a grammar, in the notation Chomsky's work led to. The Python and the grammar say the same thing. The grammar is shorter; the Python runs.

Moving between the two is a skill this course teaches.

What syntax does not say

BinaryOp(Number(1), "?", Number(2)) is a perfectly good tree.

Syntax does not say that x has a value, that division by zero is forbidden, or that + adds.

Syntax says which trees exist. It is deliberately silent about what they mean.

Half two

Semantics: what a tree means

The meaning of an expression

…is a number — once we know the value of every variable.

So the meaning of a tree is a function from an environment (a table from names to values) to a number.


type Env = dict[str, float]

def evaluate(expr: Expr, env: Env) -> float:
    ...

One case per kind of node


def evaluate(expr: Expr, env: Env) -> float:
    match expr:
        case Number(value):
            return value
        case Variable(name):
            if name not in env:
                raise NameError(f"variable '{name}' is not defined")
            return env[name]
        case BinaryOp(left, operator, right):
            lv = evaluate(left, env)
            rv = evaluate(right, env)
            match operator:
                case "+": return lv + rv
                case "-": return lv - rv
                case "*": return lv * rv
                case "/": return lv / rv
                case _: raise ValueError(f"unknown operator '{operator}'")

It runs


>>> evaluate(example, {"x": 4.0})
14.0

Three things to stare at. The whole course is in them.

1. The shape of the function is the shape of the syntax

One case per kind of node, nothing else. match takes the tree apart: case BinaryOp(left, operator, right) names the three children.

Add a kind of node to Expr → add a case to evaluate.

Not a coincidence of Python. This is what a definition of meaning looks like.

2. Recursive exactly where the syntax is

\( ⟦e_1 + e_2⟧\rho \;=\; ⟦e_1⟧\rho + ⟦e_2⟧\rho \)

"The meaning of the tree e₁ + e₂ in environment ρ is the sum of the meanings of the subtrees."

The + on the left is a piece of syntax. The + on the right is addition of numbers.

The equation and the line case "+": return lv + rv say the same thing.

3. The decisions are visible

A missing variable: we raise. A spreadsheet returns 0. A computer algebra system leaves x in the answer.

1 / 0: right now, whatever Python does.

None of these is forced by the syntax. Each is a decision about what the language means. A designer who has not made them has not finished designing.

Same characters, different trees


left_first  = BinaryOp(BinaryOp(Number(2), "*", Number(3)), "+", Number(4))
right_first = BinaryOp(Number(2), "*", BinaryOp(Number(3), "+", Number(4)))

>>> evaluate(left_first, {}), evaluate(right_first, {})
(10.0, 14.0)

evaluate does not know about precedence and does not need to. Precedence is a rule about which tree a string stands for: it belongs to the parser.

Keeping the two apart lets you change the surface of a language without touching its meaning — and the other way round.

Practical matters

How this course works

What you build

You pick an application domain — images, music, geometry, graphs, sound, text, 3D models, or one you propose — and design a domain-specific language for it:

  • analyse the domain and choose its primitives;
  • decide their semantics;
  • build an interpreter, and make the results visible;
  • write examples that show the language is good for something.

How you are assessed

  • Midway submission (1/3). Required and graded: your domain, your primitives and why, a first interpreter that runs.
  • Final presentation (2/3). Slides and a live demo in front of the class, then questions on your code and on the theory.

In the presentation you say why your language is right, and where it is wrong. That last part is the exam.

Full rules: repository, folder exam/.
