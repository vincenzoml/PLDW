Half one

Syntax: which trees exist

The syntax, in Python


from dataclasses import dataclass

@dataclass(frozen=True)
class Number:
    value: float

@dataclass(frozen=True)
class Variable:
    name: str

@dataclass(frozen=True)
class BinaryOp:
    left: Expr
    operator: str
    right: Expr

type Expr = Number | Variable | BinaryOp

Read the last line as a definition

An expression is a number, or a variable, or a binary operation — and nothing else.

The tree for 2 + (x * 3)


example = BinaryOp(
    left=Number(2.0),
    operator="+",
    right=BinaryOp(left=Variable("x"), operator="*", right=Number(3.0)),
)

A BinaryOp contains two further expressions: the definition is recursive, so trees of any depth exist.

frozen=True: a tree never changes after it is built. (Chapter 2 says why.)

The same thing, as a mathematician writes it

\( e ::= n \;\mid\; x \;\mid\; e \; \mathit{op} \; e \)

"An expression is a numeral, or a name, or an expression, an operator and an expression."

This is a grammar, in the notation Chomsky's work led to. The Python and the grammar say the same thing. The grammar is shorter; the Python runs.

Moving between the two is a skill this course teaches.

A grammar, with production rules

Production rules


Expr  ::= Var | Int | Expr + Expr
        | let Var = Expr | ( Expr )
Var   ::= x | y | z | …
Int   ::= Digit | Digit Int
Digit ::= 0 | 1 | … | 9

A derivation


Expr
→ let Var = Expr
→ let z = Expr
→ let z = ( Expr )
→ let z = ( Expr + Expr )
→ let z = ( Var + Expr )
→ let z = ( x + Expr )
→ let z = ( x + Int )
→ let z = ( x + Digit Int )
→ let z = ( x + 4 Int )
→ let z = ( x + 4 2 )

Derivation and parsing

DERIVATION · grammar → string

Derivation generates a string: repeatedly replace a non-terminal symbol using a production rule, until all symbols are terminal.

PARSING · string → rules

Parsing goes the other way: given a string, find a set of rule choices that derives it.

We will not study parsing algorithms. From Chapter 3 on, a parser generator does it for us, from the grammar.

What syntax does not say

An ice cream, divided by zero. A perfectly good tree.

Syntax does not say

that an ice cream can be divided at all,

that division by zero is forbidden,

or that ÷ divides.

Syntax says which trees exist. It is deliberately silent about what they mean.

The meaning of an expression

…is a number — once we know the value of every variable.

So the meaning of a tree is a function from an environment (a table from names to values) to a number.


type Env = dict[str, float]

def evaluate(expr: Expr, env: Env) -> float:
    ...

One case per kind of node


def evaluate(expr: Expr, env: Env) -> float:
    match expr:
        case Number(value):
            return value
        case Variable(name):
            if name not in env:
                raise NameError(f"variable '{name}' is not defined")
            return env[name]
        case BinaryOp(left, operator, right):
            lv = evaluate(left, env)
            rv = evaluate(right, env)
            match operator:
                case "+": return lv + rv
                case "-": return lv - rv
                case "*": return lv * rv
                case "/": return lv / rv
                case _: raise ValueError(f"unknown operator '{operator}'")

It runs


>>> evaluate(example, {"x": 4.0})
14.0

01
The shape of the function is the shape of the syntax

One case per kind of node, nothing else. match takes the tree apart: case BinaryOp(left, operator, right) names the three children.

Add a kind of node to Expr → add a case to evaluate.

Not a coincidence of Python. This is what a definition of meaning looks like.

02
Recursive exactly where the syntax is

\( ⟦e_1 + e_2⟧\rho \;=\; ⟦e_1⟧\rho + ⟦e_2⟧\rho \)

"The meaning of the tree e₁ + e₂ in environment ρ is the sum of the meanings of the subtrees."

The + on the left is a piece of syntax.

The + on the right is addition of numbers.

The equation and the line case "+": return lv + rv say the same thing.

Same characters, different trees


left_first  = BinaryOp(BinaryOp(Number(2), "*", Number(3)), "+", Number(4))
right_first = BinaryOp(Number(2), "*", BinaryOp(Number(3), "+", Number(4)))

>>> evaluate(left_first, {}), evaluate(right_first, {})
(10.0, 14.0)

evaluate does not know about precedence and does not need to. Precedence is a rule about which tree a string stands for: it belongs to the parser.

Keeping the two apart lets you change the surface of a language without touching its meaning — and the other way round.

Beyond calculators

Why semantics, in practice

Example: variable assignment

C-like syntax: x = 3. What does it do? Modify the memory!

How do we formalise it?

Memory is a partial function from variables to values.*

* this is not even precise — we will study it in detail.

What is memory update, formally?

x = k is interpreted as \( \mathit{update}(\mathit{mem}, x, k) = \mathit{mem}' \) where

\( \mathit{mem}'(x) = k \)

\( \mathit{mem}'(y) = \mathit{mem}(y) \text{ if } y \neq x \)

Q: mathematically, to which set do mem and mem′ belong?

\( \mathit{Var} \rightharpoonup \mathit{Val} \): the partial functions from variables to values.

Why am I mentioning all this?

In hardware, memory update changes one cell. Access time stays constant.

Now implement memory as a chain of function updates, as on the previous slide: each lookup asks the newest function, which asks the previous one, which…

Access time is linear in the number of previous updates. Crazy!

Easy to fix?

Just use arrays for memory, and array update in place of functional update.

BUT

then it is no longer formalised. Program semantics is the way to formalise arrays — so using arrays to formalise program semantics is circular.

WAY OUT: ABSTRACTION

put memory operations in a module, class or library; define them inefficiently, to study the language; define them efficiently, at a second stage.

Observing a system

Consider a system — not even "programmed", any system in the universe. How do we analyse its behaviour? Via observations. Quite obvious.

When the system is a programming language, the observations are the semantics:

\( \mathit{SEM} : \mathit{PROG} \to D \)

Q: what is D? The semantic domain.
