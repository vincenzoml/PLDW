The calculator, by hand

The exercise


def calc(text: str) -> int: ...

calc("2 + 5 - 3")      # 4
calc("10 - 4 - 3")     # 3: left to right
calc("7")              # 7
calc("2 + + 3")        # error: not well formed

  1. Integers, + and - only; no parentheses. Compute from left to right.
  2. Start with spaces between numbers and operators: text.split() gives the pieces.
  3. If the text is not well formed, raise a ValueError that says what is wrong.

Then make it work without spaces too: "2+5-3". The solution is in code/lesson-03/calculator.py.

The program, and its functions

tokenize(text) → list[str]

Cuts the text into numbers and operators, skipping spaces.

compute(pieces) → int

Checks that numbers and operators alternate, and keeps a running total from left to right.

number(piece) → int

Called by compute on each number: checks that it is made of digits, then converts it.

The first version uses text.split() in place of tokenize. The next slides go through the functions one at a time.

With spaces: split, then one loop


def compute(pieces: list[str]) -> int:
    if pieces == []:
        raise ValueError("empty expression")
    total = number(pieces[0])
    for i in range(1, len(pieces), 2):
        op = pieces[i]
        if op not in ("+", "-"):
            raise ValueError(f"expected + or -, found {op!r}")
        if i + 1 == len(pieces):
            raise ValueError(f"missing number after {op!r}")
        n = number(pieces[i + 1])
        if op == "+":
            total = total + n
        else:
            total = total - n
    return total

def calc_with_spaces(text: str) -> int:
    return compute(text.split())

A well-formed list of pieces alternates: number, operator, number, …, number.

Numbers are at even positions, operators at odd positions. The loop visits the operators: range(1, len(pieces), 2).

total holds the value of everything read so far.

Checking the numbers


int("+3")      # 3

DIGITS = "0123456789"

def number(piece: str) -> int:
    if piece == "" or any(c not in DIGITS for c in piece):
        raise ValueError(f"expected a number, found {piece!r}")
    return int(piece)

int reads Python's integers, which are not the same as ours.

With int alone, "2 + +3" would give 5: the piece +3 is accepted as a number.

So we check that the piece is made of digits, and only then call int.

str.isdigit() also accepts characters like ², on which int fails.

Without spaces


def tokenize(text: str) -> list[str]:
    tokens = []
    i = 0
    while i < len(text):
        c = text[i]
        if c == " ":
            i += 1
        elif c in "+-*()":
            tokens.append(c)
            i += 1
        elif c in DIGITS:
            j = i
            while j < len(text) and text[j] in DIGITS:
                j += 1
            tokens.append(text[i:j])
            i = j
        else:
            raise ValueError(f"unexpected character {c!r} at position {i}")
    return tokens

def calc(text: str) -> int:
    return compute(tokenize(text))

"2+5-3".split() gives ['2+5-3']: one piece.

We cut the text ourselves, one character at a time. An operator is one character; a number goes on while there are digits.

tokenize("12+5 - 3") gives ['12', '+', '5', '-', '3'], and compute does not change.

The pieces are called tokens. Cutting text into tokens is the first stage of every interpreter.

Adding *: left to right is wrong


        elif op == "*":
            total = total * n

One more branch in the loop, and 2 + 5 * 3 gives 21.

In arithmetic it is 17: * binds tighter than + and -. This is called precedence.

A single running total cannot do this. When the loop reads 2 +, it does not yet know whether the 5 that follows is a number to add or the start of a product.

Two passes


def compute_with_precedence(pieces: list[str]) -> int:
    pieces = list(pieces)
    i = 1
    while i < len(pieces):
        if pieces[i] == "*":
            if i + 1 == len(pieces):
                raise ValueError("missing number after '*'")
            product = number(pieces[i - 1]) * number(pieces[i + 1])
            pieces[i - 1 : i + 2] = [str(product)]
        else:
            i += 2
    return compute(pieces)

First pass: replace each a * b by its value. Second pass: compute, as before.


['2', '+', '5', '*', '3']
['2', '+', '15']
17

After a replacement i stays where it is, so 2 * 3 * 4 becomes 6 * 4 and then 24.

One pass per level of precedence. With / on the same level as *, and a power operator above it that groups to the right, the passes and their special cases grow.

Parentheses


def balanced(text: str) -> bool:
    stack = []
    for c in text:
        if c == "(":
            stack.append(c)
        elif c == ")":
            if stack == []:
                return False
            stack.pop()
    return stack == []

balanced("(1 + (2 - 3)) + 4")   # True
balanced("(1 + 2))(")           # False
balanced("(1 + 2")              # False

Only checking that the parentheses are balanced already needs a stack: a list where we add and remove at the end.

A counter would also do here, but not with more kinds of bracket, such as ( and [.

Computing the value is harder: each open parenthesis needs its own running total, kept aside until the matching ).

From the calculator to Lark

A parser from a grammar

Today we write a grammar, and a library builds the parser from it.

The library is Lark. The AST and the evaluator are still ours.

Four stages

The code is in code/lesson-03/; the main file is mini_interpreter.py.

What the language looks like

The grammar

A grammar in Lark


from lark import Lark, Token, Tree

grammar = r"""
    expr: bin | mono
    mono: ground | paren
    paren: "(" expr ")"
    bin: expr OP mono
    ground: NUMBER

    NUMBER: /[0-9]+/
    OP: "+" | "-" | "*" | "/" | "%"

    %import common.WS
    %ignore WS
"""

parser = Lark(grammar, start="expr")

Lark uses a variant of EBNF.

Terminals (upper case): the pieces of text, each defined by a regular expression or by strings.

Rules (lower case): how terminals and rules combine.

%ignore WS skips white space: 1+2 and 1 + 2 give the same result.

The rules, bottom up

01ground: NUMBER
A number: one or more digits. No sign.
02paren: "(" expr ")"
An expression in parentheses. The rule refers back to expr, so expressions can nest.
03mono: ground | paren
A number or a parenthesized expression: no operator at the top level.
04bin: expr OP mono
An expression, an operator, and a mono. The two sides are different; the next slides show why.
05expr: bin | mono
Either a bin or a mono. It is the start symbol: start="expr".

What is 10-4-3?

In the left tree, the right operand of each - is a mono. Our grammar only allows this tree.

Associativity and the grammar

LEFT RECURSION

bin: expr OP mono

Only (10-4)-3 = 3. This is our grammar.

RIGHT RECURSION

bin: mono OP expr

Only 10-(4-3) = 9.

BOTH SIDES

bin: expr OP expr

Both trees are possible: the grammar is ambiguous. Lark accepts it anyway.

The evaluator only sees the tree, so the grammar decides the result.

Why not write the parser by hand?

By hand, one usually writes one function per rule (recursive descent). This works for most rules, but not for ours.

Works: the rule starts with a token


# paren: "(" expr ")"
def parse_paren(tokens, i):
    expect(tokens, i, "(")
    e, i = parse_expr(tokens, i + 1)
    expect(tokens, i, ")")
    return e, i + 1

It reads ( before calling parse_expr, so each call starts further on. The calls end when the tokens end.

Loops: the rule starts with itself


# bin: expr OP mono
def parse_bin(tokens, i):
    left, i = parse_expr(tokens, i)
    ...

parse_expr tries parse_bin, which calls parse_expr at the same i, and so on: RecursionError. This is left recursion.

Lark accepts left recursion, so we keep the grammar as written.

From parse tree to value

Why not evaluate the parse tree directly?

01 · EXTRA NODES

11 of 16 nodes carry no information

expr around bin, mono around ground: they are there for the grammar. The evaluator has no use for them.

02 · A LIBRARY TYPE

It is a Lark data structure

Every later stage would match rule names as strings, and convert '1' to 1 each time. Renaming a rule, or changing library, would break all of them.

So we convert it to the AST of the last lecture.

The AST


type Op = Literal["+", "-", "*", "/", "%"]


@dataclass(frozen=True)
class Number:
    value: int


@dataclass(frozen=True)
class BinaryExpression:
    op: Op
    left: Expression
    right: Expression


type Expression = Number | BinaryExpression

Two node classes, where the grammar has five rules and two terminals.

Number holds an int. op is one of five strings, checked by mypy.

There is no Variable node, since the grammar has no names. Class names are longer than last lecture's (BinaryExpression for BinaryOp); we use these from now on.

From parse tree to AST


def transform_parse_tree(tree: Tree) -> Expression:
    match tree:
        case Tree(data="expr", children=[subtree]):
            return transform_parse_tree(subtree)
        case Tree(data="mono", children=[subtree]):
            return transform_parse_tree(subtree)
        case Tree(data="paren", children=[subtree]):
            return transform_parse_tree(subtree)
        case Tree(data="ground",
                  children=[Token(type="NUMBER", value=digits)]):
            return Number(value=int(digits))
        ...  # the bin case: next slide
        case _:
            raise ValueError(f"Unexpected parse tree node: {tree}")

Lark's Tree and Token are ordinary classes, so we can use class patterns.

expr, mono and paren have one child: we transform the child. In ground the token is text, converted here to int.

The last case should never run. It catches a mismatch between the grammar and this function.

The bin case


        case Tree(
            data="bin",
            children=[
                left,
                Token(type="OP", value="+" | "-" | "*" | "/" | "%" as op),
                right,
            ],
        ):
            return BinaryExpression(
                op=op,
                left=transform_parse_tree(left),
                right=transform_parse_tree(right),
            )

This is the only case that builds a node with children. "+" | … as op checks that the token is an operator and binds it to op. The grammar already ensures this; the pattern also narrows op from str to Op for the type checker.

The AST of (1+2)-3


def parse_ast(expression: str) -> Expression:

Alternative: Lark's Transformer


class ToAST(Transformer):
    def ground(self, children):
        return Number(int(children[0]))

    def bin(self, children):
        left, op, right = children
        return BinaryExpression(str(op), left, right)

    def mono(self, children):
        return children[0]

    def expr(self, children):
        return children[0]

    # no method for `paren`

print(ToAST().transform(parser.parse("(1+2)-3")))

Lark's own mechanism: one method per rule, found by name.


BinaryExpression(op='-',
  left=Tree('paren', [BinaryExpression(...)]),
  right=Number(value=3))

If a rule has no method, there is no error: its Lark Tree stays inside the AST.

The evaluator


def evaluate(ast: Expression) -> int:
    match ast:
        case Number(value):
            return value
        case BinaryExpression(op, left, right):
            left_value = evaluate(left)
            right_value = evaluate(right)
            match op:
                case "+":
                    return left_value + right_value
                ...  # "-" and "*" alike; "/", "%": next slide
                case _:
                    assert_never(op)
        case _:
            assert_never(ast)

\( ⟦n⟧ = n \)
\( ⟦e_1 \mathbin{op} e_2⟧ = ⟦e_1⟧ \mathbin{op} ⟦e_2⟧ \)

On the right, op is the operation on Python integers.

One assert_never for the node types, one for the operators. If Op gets a sixth operator and this match does not, mypy reports an error.

What is (0-7)/2?


                case "/":
                    if right_value == 0:
                        raise ValueError("Division by zero")
                    return left_value // right_value
                case "%":
                    if right_value == 0:
                        raise ValueError("Division by zero")
                    return left_value % right_value

Values are int, so the result cannot be -3.5. Which integer?

Here -4: // rounds towards minus infinity. C and Java truncate, giving -3.

We use Python's // and %, for which \( a = (a / b) \cdot b + a \bmod b \) holds. With truncation, % would have to change too.

Three kinds of error

1 · SYNTAX ERROR

Raised by Lark before evaluation: 1 + is not a program.

2 · INTERNAL ERROR

Unexpected parse tree node: the grammar and the transform disagree. This is a bug in the interpreter.

3 · RUNTIME ERROR

1/(2-2) is a valid program with no value. We raise a ValueError.

Without the check, Python would raise ZeroDivisionError. We raise our own error so that the language defines it. Returning infinity or 0 would also be possible; the language has to pick one.

Another decision in the grammar

Precedence

What is 1+2*3?

With a single OP and a single bin rule, all operators have the same priority. Like associativity, precedence is fixed by the grammar.

One rule per level


grammar_prec = r"""
    ?expr: sum
    ?sum: sum ADDOP prod   -> bin
        | prod
    ?prod: prod MULOP mono -> bin
         | mono
    ?mono: ground | paren
    paren: "(" expr ")"
    ground: NUMBER
    NUMBER: /[0-9]+/
    ADDOP: "+" | "-"
    MULOP: "*" | "/" | "%"
    %import common.WS
    %ignore WS
"""

No + inside a prod without parentheses: 1+2*3 is 7. ? removes one-child nodes; -> bin renames. precedence.py reuses the AST and evaluate.

Alternative: LALR instead of Earley


earley = Lark(grammar, start="expr")  # the default
lalr = Lark(grammar, start="expr", parser="lalr")
text = "+".join(["1"] * 3000)
      

earley: 0.115 s
lalr: 0.010 s

EARLEY · THE DEFAULT

Accepts any context-free grammar, including ambiguous ones. Slower.

LALR

A single pass; about ten times faster here. It rejects some grammars with a GrammarError, and resolves the ambiguity of expr OP expr without warning.

Our inputs are short and the grammar will change, so we keep the default. Timings from alternatives.py on one laptop.

def REPL() -> None:

Adding comparisons


grammar_cmp = r"""
    ?expr: cmp
    ?cmp: sum CMPOP sum    -> compare
        | sum
    ?sum: sum ADDOP prod   -> bin
        | prod
    ...
    CMPOP: "<" | "<=" | "=="
"""

type CmpOp = Literal["<", "<=", "=="]
@dataclass(frozen=True)
class Comparison:
    op: CmpOp
    left: Expression
    right: Expression

type Expression = Number | BinaryExpression | Comparison

A new level, looser than +: 1+2 <= 3 compares two sums.

The rule is sum CMPOP sum, so the level is non-associative: 1 < 2 < 3 is a syntax error.

Python reads it as 1 < 2 and 2 < 3, C as (1 < 2) < 3. We do not allow it.

What is 1 < 2?


        case Comparison(op, left, right):
            a, b = evaluate(left), evaluate(right)
            match op:
                case "<":
                    return int(a < b)
                case "<=":
                    return int(a <= b)
                case "==":
                    return int(a == b)
                case _:
                    assert_never(op)
      

evaluate_cmp("1+2*3 < 10")      # 1
evaluate_cmp("(1<2) + (2<1)")   # 1

1, as in C. All values are still int, and evaluate keeps its return type.

Returning True would mean values are int or bool, and we would have to define (1<2) + 1.

Which values a language has is a separate topic, for a later lecture.
